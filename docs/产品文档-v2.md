## 1. 产品定义

### 1.1 一句话

凤翎工坊是一个**面向小说创作者的世界可视化平台（MVP）**：不懂编程的作者，只需通过拖拽操作+对AI下达自然语言指令，就能将自己的小说转化为读者可进入探索的2D像素世界；读者点击链接后，直接在浏览器中游玩，无需安装任何程序。

### 1.2 双层结构（理解这个产品的关键）

仓库里住着两样东西，它们是**工具和作品**的关系：

| 层 | 是什么 | 面向谁 |
|---|---|---|
| **《07 号调查员》** | 一款可游玩的悬疑叙事Demo，设定于2095年，融合AI协同文明与SCP风格的「异常区域」，玩家可进入世界与NPC对话、收集线索、解锁后续篇章 | 读者 / 体验者 |
| **凤翎工坊编辑器** | 用于制作上述Demo的编辑器，支持地图、NPC、对话、玩法机制的全可视化配置 | 创作者 |

关键点：**该Demo并非通过手写代码堆砌而成，而是创作者使用凤翎工坊编辑器制作的样品**。这是产品可信度的来源——工具能不能用，看它自己产出的东西。

> 类比：这就如同面包机厂商展示的不是产品设计图，而是用自家面包机烤出的成品面包。

### 1.3 它解决什么问题

网络小说作者仅能依靠文字创作，若想让读者感知世界观的立体感，常规做法要么是请美术绘制设定集（成本高、形式静态），要么是找团队开发游戏（成本更高、周期以年计算），两者之间存在明显的空白地带。

现有关卡编辑器（[LDtk](https://ldtk.io/) / [Tiled](https://www.mapeditor.org/)）虽可制作地图，但均面向游戏开发者：需安装桌面软件、理解图层与瓦片概念，导出后还需自行编写引擎代码对接，普通作者难以跨越这道门槛。

凤翎工坊的取舍逻辑是：**功能仅保留叙事探索所需的核心能力，交互设计降至无需学习即可上手**——浏览器打开即可使用，支持拖拽摆放元素、通过表单配置对话、以自然语言指令让AI完成相关操作，最终一键生成分享链接。

### 1.4 术语表（后文会反复出现）

| 术语 | 人话解释 |
|---|---|
| **章节 / chapter** | 可进入的独立场景（一间屋子、一片城区），对应数据中 `chapters.json` 的一条记录 |
| **区域图 area** | 特殊章节，指一整片户外大地图（如临澜城），内部设有若干「大门」，可通往具体场景 |
| **格 / grid** | 地图按16像素切割为方格，人物以格为单位移动，所有坐标均为格坐标 |
| **walkable（通行层）** | 与地图尺寸一致的0/1表格，用于标记哪些方格可通行、哪些为墙体 |
| **footprint（碰撞脚印）** | 建筑的视觉图可能较高，但实际阻挡路径的仅为底部几行，footprint即指该底部几行的数值 |
| **y-sort（前后遮挡）** | 人物走到建筑后方时会被建筑遮挡，走到前方时则覆盖建筑，通过Y坐标排序实现该效果 |
| **战雾 fog** | 世界地图中未开放区域的黑色遮罩（塞尔达风格），小说剧情推进到哪里，对应地图区域就会点亮 |
| **触发器 trigger** | 即「玩家执行某操作→触发某事件」的规则，在产品中被封装为「机制卡」 |
| **线索 clue** | 玩家发现后会记入「调查日志」的信息，也是解锁后续内容的计数单位 |
| **意图级命令** | 仅需下达「把仓库放到南门附近」这类指令，无需指定具体坐标，坐标由系统自动计算生成，见3.5节 |
| **E2E 测试** | 端到端自动化检查，通过脚本模拟真人操作完成全流程，验证结果是否正确 |

## 2. 用户与场景

### 2.1 创作者（主要用户）

两类入口需求存在差异，产品不做强制统一：

- **有现成稿件的作者**：已撰写几十万字，希望搭建世界观。理想路径是上传稿件，由AI提炼人物与地点初稿。⚠️ 此路径当前为 **mock**（见 3.9）。
- **从零构建世界的作者**：先有画面感再生成文字，希望边搭建边构思。当前主路径为——新建项目时从「起手式模板」开始。

共同特征：**不写代码，也无意学习代码**。因此产品的每一项功能都必须提供非代码操作入口（拖拽、表单、下拉框、自然语言交互）。

### 2.2 读者（次要用户，不付费）

打开作者分享的链接即可直接体验，无需注册或安装，进度存储在用户本地浏览器中。读者体验做好了，作者才有分享动力——这是产品的核心传播逻辑。

### 2.3 创作者路径（6 步，已跑通）

```
① 新建项目（选起手式模板：空白 / 调查推理 / 对话抉择）
   ↓
② 拖拽搭建场景（建筑 / 物件 / NPC / 传送门，所见即所得）
   ↓
③ 表单配对话（分支选项、条件对话页「它记得你来过」）
   ↓
④ 机制卡配玩法（当…→如果…→就…）
   ↓
⑤ ▶ 一键试玩（直接进入游戏现场体验）
   ↓
⑥ 📤 发布（机器校验通过 → 生成只读分享链接）
```

②、③、④ 三步均可通过自然语言与 AI 交互完成（见 3.5）。⑥ 的校验是**真实有效的**，并非形式化流程：会检查出生点是否为墙体、各出口是否可通行、数据是否完整，未通过校验则无法生成分享链接。

### 2.4 读者循环（core loop）

```
世界地图（战雾）→ 点亮的地点进入现场 → 走近 NPC 对话 / 查看物件
   → 做选择、拿线索进「调查日志」 → 线索攒够，新地点显影解锁
   → 找到道具（如值守密卡）打开原本锁着的门 → 更深处
```

这是叙事探索品类（walking sim）的标准循环：**探索 → 发现 → 日志外显 → 解锁 → 再探索**。产品刻意未加入战斗和数值系统——这类设计属于其他品类，加入后会稀释叙事核心。

### 3.1 世界搭建

编辑器入口：`index.html?edit=章节id`（如 `?edit=area_city`）。三栏 IDE 布局——顶栏功能条、左栏工具、中间画板、右栏 Inspector（属性面板）。

| 能力 | 说明 |
|---|---|
| 底图模式 | 一整张 AI 生成的场景图铺底，碰撞层独立于图像。适合户外大地图 |
| 瓦片模式 | 用 16px 小图块拼地面 + 立体墙。适合室内小房间 |
| 拖拽摆放 | 物件 / NPC / 出生点 / 传送门，鼠标拖到哪就在哪，松手即写入数据 |
| 碰撞刷子 | 左栏「🧱 墙 / ⬜ 可走」，鼠标在画板上刷，所见即所得 |
| 物件属性 | Inspector 配：名称、碰撞底层数（footprint）、能否交互、交互文案、给予道具、需要道具、复制物件 |
| 传送门 | 可拖动、可改门牌名，指向另一章节；可设为需要道具才能通过 |
| 保存防呆 | 保存前跑连通性检查：把出生点堵死、或某个出口走不到，**直接拒绝保存**并提示 |
| 角色尺寸工作台 | 全局设置主角和每个 NPC 的显示尺寸，带**参照物预览**——把真实底图和建筑铺出来，角色一排站开对比（"大小是相对的"） |
| 镜头跟随 | 地图大于视口时，主角恒定居中，镜头跟着走 |
| y-sort 遮挡 + 遮挡渐隐 | 走到楼后面被挡住；完全挡住时那栋楼自动半透明，防止玩家找不到自己 |

**分层生成范式**（决定了美术怎么做）：
- **L0 地貌层** — AI 只生成纯地形，默认全部可走
- **L1 物件层** — 建筑单体是透明底的独立图片，编辑器摆放，碰撞由 footprint 显式声明
- **L2 角色层** — 角色独立 sprite

早期版本将建筑直接嵌入整张底图，再通过像素统计反推可通行区域，结果是玩家撞到看不见的空气墙。分层之后碰撞是**声明出来的**而不是**猜出来的**，这类问题从根上消失。

### 3.2 NPC 系统

| 能力 | 数据字段 | 说明 |
|---|---|---|
| 行为枚举 | `behavior: static / wander / patrol` | 静止（可设朝向）/ 在出生点附近随机游走（可设范围）/ 沿路径点巡逻 |
| 分支对话 | `dialogue.nodes[]` | 每个节点有说话人、台词、走向；`choices` 生成玩家选项，选择记入「分支痕迹」 |
| 条件对话页 | `dialogPages[]` | 从上往下取第一个条件满足的页，最后一页必须无条件兜底 |
| 节点级静默指令 | `node.do[]` | 说到某句话时顺手记条线索、设个标志位 |

**条件对话页**是「NPC 记得你来过」的实现方式，借鉴 RPG Maker 的事件页范式。可用条件：持有某标志位、线索数达到 N、访问过某章节、持有某道具。

行为由定时器驱动，不依赖渲染帧——所以在无头浏览器里跑自动化测试时 NPC 照样会动。对话进行时所有 NPC 均会暂停，避免 NPC 移动导致对话中途中断。

### 3.3 交互系统与机制卡

这是「不写代码配出游戏逻辑」的核心。

**触发时机**：
- `interact` — 走近 + 按空格。挂在 NPC 和物件身上
- `enter` — 走进指定矩形区域
- `leave` — 离开指定区域
- `auto` — 进入场景立即执行（开场独白、氛围特效）

后三种存在章节的 `triggers[]` 里，都支持**条件**（标志位 / 线索数 / 已访问 / 持有道具）和 **once**（只触发一次，完成状态持久化）。

**9 种指令积木**（一个小型解释器按队列顺序执行）：

| 指令 | 干什么 |
|---|---|
| `text` | 弹一句旁白或台词 |
| `choice` | 给玩家几个选项，按选择跳转 |
| `set` | 设置 / 清除一个标志位 |
| `if` | 条件分支，两条支路各自是一串指令 |
| `addClue` | 记一条线索进调查日志 |
| `giveItem` | 给玩家一件道具 |
| `teleport` | 传送到另一章节的指定位置 |
| `fx` | 播视觉特效（信号撕裂 / 镜头震动 / 闪光） |
| `wait` | 等待若干毫秒 |

**机制卡编辑器**（编辑器左栏「⚡ 机制」）把上面这套包装成三段式积木，避免创作者面对 JSON：

```
当    [走进某区域 ▾]  位置 13,14  范围 3,3      ☑ 只触发一次
如果  [持有道具 ▾]    值守密卡
就    [💬 说旁白 ▾]   凤翎-07 ｜ 「气闸响应了。」
      [📋 记一条线索 ▾] 休眠槽异常
```

选择器里全是中文人话（"一进场就触发""走进某区域""记一条线索""给道具"），不出现任何变量名或代码。数据落回同一个 `triggers[]` 数组——**机制卡仅为一层 UI，并非独立运行时**，因此它与游戏引擎之间不会出现偏差。

### 3.4 玩法机制

**调查日志**：玩家发现的线索按渐进列表展示——已揭露的是可点开的青绿卡片，未揭露的是 `▒▒` 占位（"还有多少没找到"本身就是驱动力）。新线索触发解锁动画 + 提示。对标 Outer Wilds 的 Ship Log，但用列表而非网络图（网络图工期翻倍，列表已够支撑核心循环）。

**叙事道具**：物件或 NPC 可以 `givesItem` 给道具；传送门和物件可以 `requiresItem` 要求道具，没有就弹自定义提示文案。这让「你得先找到 X 才能打开 Y」成立——叙事探索品类最基本的关卡设计手段。

demo 中的完整闭环：监测带补给箱 → 发放「值守密卡」→ 解锁 6 号站气闸门 → 进门播放两段文本 → 记录一条线索 → 世界地图新增地点显影。

**世界地图渐进解锁**：地点按 `requires`（需要的线索数）逐步显影，配显影动画；未开放区域是整片战雾。

### 3.5 AI 命令层

编辑器顶栏「⌘ AI 命令」抽屉，输入自然语言：

```
把市集大棚放到管理局总部附近
让 FS-7800 在广场附近巡逻
让陈伯原地待命
```

**核心设计：编辑器 UI 和 AI 是同一套 API 的两个客户端。**

```
创作者说人话 ──→ AI 翻译成意图 ┐
                                ├─→ POST /api/command ─→ chapters.json ─→ 编辑器热更新
创作者鼠标拖 ──────────────────┘
```

两个遥控器，一台电视。这样做的好处是 AI 不会走后门——它能做的操作和手动能做的完全一致，也就无法绕过校验搞出坏数据。

**AI 只输出意图，不碰坐标。** `place_prop { type: "市集大棚", near: "管理局总部" }` 里没有任何数字。坐标交给服务端螺旋搜索，逐个候选位置验：不出界、不和已有物件重叠、不压住街道超过阈值、不挡住门和 NPC、烧录碰撞后所有出口仍然连通。找不到合法位就明确报错，不硬塞。

> 为什么这么切分：让语言模型算格子坐标是它最不擅长的事（会算错、会撞墙）；让它理解"市集大棚""南门附近"是它最擅长的事。各干各的。

**解析链路**：DeepSeek（可选，读取项目根目录 `.ai_key`）→ 若失败或未配置，则降级至内置规则解析器，支持识别“把 X 放到 Y 附近”“让 X 巡逻/游走/停下”等固定句式。不配 key 功能不中断，界面上有徽章标明当前用的是哪个引擎。

已注册意图：`place_prop`、`set_npc_behavior`、`bake_semantics`（烘焙语义层）、`compile_walkable`（重编译通行层）。

### 3.6 语义层

**病根**：早期将 `walkable`（通行层）作为原始数据直接存储并手动修改。但它其实是**推导出来的结果**——地形能不能走 + 物件占了哪几格。把结果当事实存，就会和画面脱节：楼骑在马路上、通行层和图对不齐。

**改法**：`room.semantics = { ground, roads }` 升级为原始事实，`walkable` 降级为编译产物。

```
地形语义（哪里是地面/街道）  ┐
                              ├─→ 编译 ─→ walkable
物件 footprint（谁占了哪几格）┘
```

编辑器左栏「语义层」包含三个按钮：
- **🛣 街道叠加** — 实时分析底图亮度识别街道，绿色高亮显示。拖楼压到街上超过阈值会警告
- **🧭 烘焙语义** — 把识别结果转正存盘
- **⚙ 编译通行** — 从语义 + 物件碰撞重新烧出 walkable，编译前后都跑连通性检查，会破坏连通就拒绝写盘

**状态**：临澜城已完成正式烘焙（共 1297 格街道），其余章节采用兼容路径（直接使用现有 walkable），两种模式并存且不冲突。这是有意的渐进迁移——老数据不作废。

### 3.7 发布与分享

点击「📤 发布」将触发聚合校验（为真实校验，非装饰性流程）：

1. 数据完整性（章节字段齐不齐）
2. 出生点不是墙
3. 从出生点能走到每一个出口（BFS 连通）
4. 每个出口指向的章节真实存在
5. 至少有一个可玩单元（NPC / 可交互物件）

通过 → 弹绿卡，给只读分享链接 `?play=project`，带复制和预览。
不通过 → 弹红卡，逐条列出问题，**不给链接**。

**读者模式**（`?play=`）：隐藏编辑器入口，显示「📖 只读试玩」徽章，返回键变为「↻ 从头开始」。校验和读者模式全程只读，不写盘。

**导出 zip / 上传托管**是 mock（弹提示说明正式版会怎么做），保留入口是为了让“作品可以脱离平台分发”这个方向有个可指的位置。

### 3.8 两种创作模式

| 模式 | 状态 | 说明 |
|---|---|---|
| **地图探索** | ✅ 完整 | 本文档主要描述的这套。有地图、有网格、走进去 |
| **事件主导** | ✅ 可体验 | 视觉小说式播放器，无网格：场景字幕 + 对话框 + 分支选项。配套节点编辑器，支持修改文案、说话人、选项、增删结尾节点，且预览内容暂不落地 |
| **时间线** | ⬜ 占位 | Landing 上标「敬请期待」 |
| **群像关系图** | ⬜ 占位 | 同上 |

事件主导模式在 demo 中的样品为番外《值守舱 · 02:47》：包含 7 个节点、2 个分支结局。它证明的是“同一套数据底座能长出不同的呈现形态”——不是所有小说都适合走地图。

### 3.9 平台首页与新建项目

Landing（`http://127.0.0.1:8131/`）是默认入口：品牌英雄区 + 上传区 + 四种创作模式卡片 + 我的项目。

**新建项目 = 模板选择器**（这是「引导即模板」的设计选择）：

| 模板 | 里面有什么 | 教会什么 |
|---|---|---|
| ▧ 空白项目 | 一个四面墙的空房间 + 一个待写台词的单元 | 从零开始的自由度 |
| 🔍 调查推理 · 起手式 | 一位目击者 + 一份可翻阅的档案 + 进场即触发的旁白 + 一条线索 | 「探索 → 对话 → 线索」怎么串 |
| 💬 对话抉择 · 起手式 | 两位 NPC：和旧友说过话，守门人就"记得你来过" | 条件对话页 + 标志位，多结局的地基 |

**为何不提供空房间模板**：新手进入空房间会无从下手，因为不清楚“成品该是什么样子”。每个模板都是**能直接点▶试玩的最小完整场景**——先玩一遍，再拆开改，比读文档快得多。

**小说上传→AI 解析为 mock 功能**：包含真实的文件选择器、文件名回显，解析结果的数值从现有数据动态计算，但提取的人物、地点为预设内容，未对接真实大模型。界面上标了 mock 徽章。

## 4. 数据模型

### 4.1 单一数据源 `chapters.json`

**游戏的全部内容——剧情、地图、NPC、对话、机制、线索、道具——都整合在这一个文件中。修改内容无需接触代码。** 这是实现「不懂编程也能创作」的技术基础。

```
chapters[]                      每章 = 一个可进入的场景
  id / title / name / place     标识与展示
  locked / requires             锁态与解锁所需线索数
  area                          true = 户外区域大地图
  room:
    cols, rows, spawn[x,y]      尺寸与出生点
    bgImage?                    底图路径（底图模式）
    floor? / innerWalls?        瓦片地面与内墙（瓦片模式）
    walkable[]                  通行层，每行一个「1墙0走」格式的字符串 ← 编译产物
    semantics?                  { ground, roads } ← 原始事实（已烘焙的章节才有）
    actorSize?                  本章角色尺寸覆盖
    effects?                    异常氛围层
  npcs[]    { id, name, pos, sprite?, behavior?, dialogue, dialogPages? }
  props[]   { id, name, pos, size, sprite?, footprint?, movable?,
              isInteractable?, interactText?, givesItemId?, requiresItem?, actions? }
  triggers[]{ id, type(auto/enter/leave), at, area?, once?, conditions?, actions[] }
  gates[]   { at, to, label, spawnAt?, requiresItem?, lockHint? }
  clues[]   { id, name, detail }

worldmapV2  大陆图 / 8 片战雾 / 开放区域与其中的地点
eventDemo   事件主导模式的样品数据
settings    { actorSize, npcSizes }  全局设置
```

**三级尺寸优先级**：`room.actorSize`（本章覆盖）→ `settings.actorSize`（全局）→ 引擎默认。NPC 额外增加一级 `settings.npcSizes[id]`。这种设计同时满足「逐图设置太繁琐」和「某张图需要例外」两种需求。

### 4.2 玩家进度（localStorage）

服务端不存储任何玩家数据，所有进度都保存在玩家的浏览器本地。清除 localStorage 即相当于重新开始一局游戏。

| 键 | 存什么 |
|---|---|
| `fs01_records` | 线索收集情况、解锁状态、私人记录 |
| `fs01_flags` | 标志位（"某事发生过没有"） |
| `fs01_inventory` | 持有的道具 |
| `fs01_clues_revealed` | 已揭露的线索 |
| `fs01_triggers_done` | once 触发器的完成记录 |
| `fs01_visited` | 访问过的章节 |
| `fs01_branches` | 分支选择痕迹 |
| `fs01_revealed_seen` | 显影动画是否已播过 |

## 5. 技术架构

### 5.1 分层

| 层 | 技术 | 一句话 |
|---|---|---|
| 平台首页 / 世界地图 | **纯 DOM** | 高清矢量 HUD + 渐进战雾，文字清晰、响应式 |
| 游戏房间 | **Phaser 3（本地化）** | 网格移动 / 碰撞 / y-sort 遮挡 / 镜头跟随 / 点击寻路 |
| 编辑器 | 纯 DOM | 三栏 IDE 布局，与游戏共用同一份数据 |
| 数据 | `chapters.json` | 单一数据源 |
| 后端 | `server.py`（**Python 标准库**） | 静态服务 + `/api/save-chapter` + `/api/command` + `/api/ai-command`，零 pip 依赖 |
| AI 解析 | DeepSeek（可选）+ 规则兜底 | 自然语言 → 意图级命令 |
| 美术管线 | Python + Pillow（离线脚本） | AI 生图 → 绿幕抠图 → 32 色量化 → 入库校验 |

**分工铁律：界面归 DOM，游戏归 Phaser。** 早期世界地图画在 Phaser 画布中，结果文字被像素缩放糊掉、窄屏还出现遮挡，拆分后各得其所。

### 5.2 三条值得讲的设计决策

**① 无构建（no build）**
没有 npm、没有打包器、没有框架。`index.html` 是单个文件，`server.py` 仅用标准库，clone 下来一行命令即可运行。

> 像一本书，翻开就能读，不用先组装书架。

代价是单文件冗长、没有模块系统。对这个体量和“给不懂技术的人 clone 下来跑”的目标而言，这笔交易划算。**这是定位，不是欠账**——想改进它的人请先理解这一点。

**② 数据驱动**
改剧情、地图、NPC、机制 = 改 `chapters.json` 或用编辑器，不碰代码。代码仅负责“怎么渲染、怎么响应”，内容全在数据里。

**③ 通行层是编译产物**
见 3.6。这条决策消灭了一整类“看起来能走其实走不了”的 bug，也是 AI 命令层敢自动摆放物件的前提——摆完自动重编译，编译前后会做连通性检查。

### 5.3 质量保障

作者是编程小白，所以**质量靠机器尺子而不是靠手感**。

```bash
python3 test/e2e_smoke.py      # 需要 server 先启动 + 本机装有 Chrome
```

用无头 Chrome + Python 断言对**真实运行的 server** 做确定性检查，最近一次全量运行 **203 项全绿**。覆盖分组：

| 组 | 查什么 |
|---|---|
| FILE | 数据完整性、素材文件存在 |
| PIXEL | 美术切割件的透明度、无残影 |
| LOAD | 各场景加载无 JS 报错 |
| DRAG / SAVE | 拖动 → 存盘 → 落地数据正确（自动备份还原） |
| AREA | 区域图连通性（BFS）、镜头、大门切场景 |
| GAMEPLAY | NPC 行为、触发器、条件对话页、线索、道具 |
| MECH | 机制卡编辑器存盘往返 |
| AICMD | AI 命令落盘、非法位置被拒 |
| SEMANTIC | 语义烘焙、通行层编译一致性 |
| PUBLISH | 发布校验通过 / 拦截、读者模式 |
| TEMPLATE | 新建项目模板闭环 |

原则：**机器能验的（数据、逻辑、连通、渲染）全部自动化；人只验美术观感和手感这类主观项。**

## 6. 边界与路线图

### 6.1 明确不做

| 不做 | 原因 |
|---|---|
| 战斗 / 数值 / 升级系统 | 叙事探索品类的反模式，会稀释叙事重心 |
| NPC 接入真实大模型自由对话 | 成本不可控，且会破坏作品克制的叙事调性——AI 即兴发挥的台词并非作者创作 |
| 读者付费解锁内容 | 读者端保持完全免费，是传播回路的前提 |
| 评论 / 点赞系统 | MVP 阶段易分散注意力，暂后置 |
| 移动端编辑器 | 读者端手机可运行，编辑功能仅支持桌面端 |
| 引入构建工具 / npm / 前端框架 | 见 5.2 ① |

### 6.2 已知局限（诚实版）

- **在线版为只读试玩**。GitHub Pages 是纯静态托管，编辑器的保存操作及 AI 指令需本地 server——体验完整编辑器请本地运行。
- **小说上传 AI 解析为 mock**，未接入真实大模型。
- **导出 zip 与订阅计费为 mock**，仅存在界面无实际功能。
- **部分场景仍为「线框模式」**：物件以青绿线框 + 名牌占位，等待美术贴图。界面有明确标注，并非 bug。
- **时间线 / 群像关系图**两种创作模式为占位。
- **美术全部由 AI 生成**后经 32 色量化，风格统一度依赖生图规格卡，并非每张都能一次成功。
- 单文件 `index.html` 体量偏大，长期维护需拆分（但拆分不能引入构建步骤，见 5.2 ①）。

### 6.3 下一步方向

| 优先级 | 方向 | 说明 |
|---|---|---|
| 高 | 小说文档 AI 解析转正 | 从 mock 切换为真实抽取人物 / 地点 / 场景，经人工审核后入库——AI 会编造关系，必须人工审核 |
| 高 | 底图上传 UI 化 | 目前 AI 生图 → 量化入库仍在脚本层，需改为编辑器内的「上传场景底图」功能 |
| 中 | 更多玩法模板 | 扩充起手式模板，覆盖更多题材 |
| 中 | 读者数据看板 | 作者可查看读者进度及流失节点 |
| 中 | 调查日志网络图 | 从渐进列表升级为线索关系网（Ship Log 风格） |
| 低 | 时间线 / 群像模式 | 第三、第四种创作模式 |
| 低 | 事件模式第一视角背景 | 目前为纯黑背景 |

## 7. 商业模式方向

**「卖铲子」：创作者付费用工具，读者端永远免费。**

核心逻辑是价值归属清晰：读者对阅读工具的付费意愿存在天花板，而创作者使用该工具是为了增强粉丝粘性、辅助 IP 展示，具备明确的业务回报。读者免费还顺带承担传播职责：作者分享链接 → 读者使用 → 更多创作者关注到。

产品里的对应实现：Landing 上有三档订阅示意（免费 / 进阶 / IP 展示），**当前全是 mock，未接支付**。免费层的项目数限制采用真实拦截逻辑，用于演示产品分层。

用于课堂讨论的核心问题是：**创作者愿意为"把小说变成可探索世界"投入多少时间**——这不是价格问题，而是时间成本问题。即便工具做得再好，若一部小说的配置需要三天才能完成，该商业模式也无法成立。这也是模板选择器、AI 命令层等功能存在的核心原因：**它们不是炫技，是在压缩创作者的启动成本。**
## 8. 上手与二次开发

### 8.1 本地运行（3 步，Mac / Windows 都行）

唯一前置：**Python 3.8+**（macOS 自带；Windows 从 python.org 或微软商店免费安装）。无需 pip，也无需 Node.js。

```bash
git clone https://github.com/roam-bit/fengling-workshop.git
cd fengling-workshop
python3 server.py            # Windows 用 python server.py
```

浏览器打开 **http://127.0.0.1:8131** 即可访问完整版。

> 未安装 Git？可在仓库页面点击 **Code → Download ZIP**，解压后同样执行 `python3 server.py`。
> **必须使用 `server.py`，不能改用 `python -m http.server`** ——编辑器的保存功能依赖它的 POST 接口，改用 http.server 会静默失效。
> **server 为常驻进程，运行时请勿关闭。** 修改前端代码后刷新浏览器即可；仅当修改 `server.py` 时才需要重启服务。

在线只读试玩（不含编辑器）：`https://roam-bit.github.io/fengling-workshop/index.html?play=project`

### 8.2 常用入口

| 用途 | 地址 |
|---|---|
| 平台首页 | `http://127.0.0.1:8131/` |
| 编辑城市大地图 | `index.html?edit=area_city` |
| 编辑室内场景 | `index.html?edit=ch4` |
| 直接进入某个房间 | `index.html?room=ch4` |
| 事件主导模式 | `index.html?event=1` |
| 读者只读模式（整个项目） | `index.html?play=project` |
| 读者只读模式（直达某场景） | `index.html?play=ch4` |

### 8.3 改内容（不碰代码）

1. 通过 `?edit=章节ID` 打开编辑器，支持拖拽修改、表单填写、机制卡配置 → 💾 保存
2. 或直接编辑 `chapters.json`（台词、NPC、机制卡数据均存储于此）

> ⚠️ 手动修改 JSON 后，需先校验语法：`python3 -c "import json;json.load(open('chapters.json'))"`。语法错误会导致页面白屏。server 每次保存会自动将备份滚动至 `backups/` 目录（保留 20 份），修改出错时可恢复。

### 8.4 用 Codex / Claude Code / Cursor 改代码

仓库根目录下的 **`AGENTS.md`** 是面向 AI 编程工具的项目地图，涵盖架构、文件分工、常见修改方案、已知问题，AI 工具会自动读取该文件，直接下达自然语言命令即可。

**给 AI 工具的两条关键提示（已写入 AGENTS.md，但课堂上仍需重点强调）：**
- 切勿让 AI 代执行 `python3 server.py`——该命令启动的是前台常驻进程，AI 会一直卡在等待状态
- 修改完成后需让 AI 执行 `python3 test/e2e_smoke.py`，需全部通过（退出码为 0）才算完成

### 8.5 三个上手练习（建议课堂用）

| 难度 | 练习内容 | 练习目标 |
|---|---|---|
| ★ | 为临澜城的陈伯添加一句台词 | 数据驱动：仅修改内容，无需接触代码 |
| ★★ | 通过机制卡实现「走近就触发旁白 + 记录一条线索」的交互点 | 触发器 → 条件 → 指令的完整执行链路 |
| ★★★ | 使用「调查推理」模板新建章节，配置一扇需道具才能开启的门并发布 | 创作者全流程（共 6 步） |

进阶任务：让 AI 添加新的指令积木类型（例如「播放音效」），需完成从数据字段 → 解释器分支 → 机制卡下拉选项 → E2E 断言的全流程，可完整体会该架构的分层设计。
